    Serialization¤

    based_datatypes.serialize turns Python objects into two families of output — files and JSON-supported values — without the caller wiring up a library per format. You describe what you have and what you want; the package picks a serializer that understands both, tells you whether the format is lossless, and can estimate how large the result would be before you produce it.

    When to use it¤

    • Serialize a dict, model, dataframe, array, image, XML tree or SQL statement without importing a different library for each format.
    • Convert values JSON cannot hold — datetime, complex, Decimal, UUID, bytes, enums — into something a JSON document can carry, and back again.
    • Read content back while declaring the type you expect, so a mismatched source fails loudly.
    • Ask for a lossless format when round-tripping matters, and accept a lossy one when it does not.
    • Budget an export before producing it.
    • Lay a serialized dictionary of files and primitives out as a directory tree.

    Quick start¤

    dict True { "hello": "world", "items": [ 1, 2 ] }

    The serializer comes from the pair: the object's type and the requested target. A dict going to application/json picks the JSON serializer; a pandas.DataFrame to text/csv picks the dataframe serializer; a datetime picks the ISO 8601 serializer, because no file is involved.

    What can be serialized¤

    Object Targets
    dict of JSON-shaped data JSON, YAML, itself
    pydantic.BaseModel JSON, YAML, dict of its dump
    pandas.DataFrame, polars.DataFrame CSV, parquet, Excel
    numpy.ndarray .npy, .npz, CSV
    PIL.Image.Image PNG, TIFF, BMP, JPEG, GIF, WebP
    xml.etree.ElementTree XML text, XML file
    bs4.BeautifulSoup HTML text, HTML file
    sqlalchemy statements SQL text, SQL file
    datetime, date, time ISO 8601 text
    timedelta a number of seconds
    complex a two-element [real, imaginary] list
    Decimal, uuid.UUID, pathlib.Path text
    bytes base64 text
    enum.Enum its value
    anything picklable pickle file

    Optional formats need the common-serializers extra:

    uv add "based-datatypes[common-serializers] @ git+https://github.com/cloudlane-one/based-datatypes.git"

    It installs the serializer implementations (numpy, pandas+pyarrow+openpyxl, polars and its Excel backends, pillow, beautifulsoup4, sqlalchemy). Formats whose library is missing simply have no serializer, so selection reports no candidate instead of failing inside the serializer.

    Values JSON cannot hold¤

    Scalars serialize to the primitive that carries them, so they can be embedded in a JSON document and read back with the annotation you expect:

    datetime.datetime(2024, 1, 2, 3, 4, 5) -> '2024-01-02T03:04:05' datetime.date(2024, 1, 2) -> '2024-01-02' (3+4j) -> [3.0, 4.0] Decimal('1.10') -> '1.10' 2024-01-02 03:04:05 (3+4j) 00000000-0000-0000-0000-000000000001 aGVsbG8=

    These serializers produce values, not files: a scalar has nothing to put in a file of its own. Embed it in a dictionary or list when you want it on disk.

    Reading back with an expected type¤

    deserialize(source, annotation) validates what it parsed against the annotation. A source that does not fit raises TypeError; a pair of source and annotation that no serializer handles raises ValueError:

    created: '2024-01-01T00:00:00' name: a

    name='a' created=datetime.datetime(2024, 1, 1, 0, 0) refused: No suitable serializer found for LocalFile[typing.Literal['application/yaml'], , based_datatypes.files.Read | based_datatypes.files.Write] as list[int] under scope Open().

    Model fields are converted with pydantic's JSON mode first, so datetime, UUID and Decimal values serialize instead of failing halfway through the write.

    Choosing a format¤

    get_serializers(typ, targets, scope, lossless) returns the (index, target, driver) triples that can handle an object, ordered by the position of the matching target — the caller's first target wins. It is what serialize and deserialize use internally, and it is the way to ask which serializer would be picked. Passing value= matches the instance against each driver's declared object type as well, which is how a list of SQL statements is told apart from [1, 2]:

    DateTimeSerializer, DateSerializer, PickleSerializer [] JSONSerializer handles dicts

    Lossless versus lossy formats¤

    Some formats reproduce the object exactly, others keep only a reduced representation. A serializer declares which of its MIME types round-trip, because one serializer can cover both: parquet keeps a dataframe's dtypes and values, CSV does not; PNG is lossless, JPEG is not.

    Pass lossless=True (the default) to require an exact round trip, lossless=False to accept a reduced one:

    PdSerializer PdSerializer

    Reading is not restricted this way: losslessness describes what an export can drop, so deserialize reads lossy formats as readily as lossless ones.

    A target that is not a file has no MIME type to declare, so a serializer states that case separately with __lossless_values__; SQL and HTML declare False, because their text target is the same lossy re-rendering as their file. Without a requested target the filter is not applied at all — serialize(obj) takes the first format the serializer declares.

    Containers¤

    A container — a mapping, a sequence, a set or a dataclass instance — reduces to a dictionary or a list, with every item serialized on its own. That is what turns values JSON cannot hold into a JSON-shaped payload: a datetime becomes its ISO 8601 text, a dataclass becomes a mapping of its fields, and an item that serializes to a file (a dataframe, an image) is nested as that file. The driver declares the dictionary and list value targets only, so a container that holds files is still a valid payload for a directory tree, while writing JSON or YAML files stays with JSONSerializer.

    {'created': '2024-01-01T12:00:00'}

    A serializer that cannot fulfil the requested target raises UnsupportedTargetError. serialize then tries the next matching serializer and raises only when none is left, so several drivers can declare the same format with different capabilities; a custom serializer implements that contract when it supports only some of the formats it declares.

    Declaring a scope¤

    The third type argument of Serializer[V, T, S] declares the scope a serializer serves. A declaration serves a request when the request is an instance of the declared scope, and every scope derives from Open: an Open declaration therefore serves every request, while a declaration for a narrower scope cannot serve an unrestricted (Open) one. A serializer that leaves S out declares Open, which is why the built-in drivers are usable everywhere.

    True

    The declaration is a class, not a value: a scope carries data (a process id, a subnet), and only the caller knows it, so the value is supplied at call time while the class is what selection compares. The scope the caller passes is what a serializer and the ambient current_ser_ctx see — never the declaration.

    Estimating the export size¤

    estimate_serialized_size(obj, target_type) reports how many bytes the serialization would produce, without writing anything. Speed wins over accuracy: an estimate only performs a full serialization when that serialization is the cheap route — a single C-level pass — and otherwise samples or bounds the payload.

    Format Basis
    JSON exact, measured with the C encoder
    YAML the compact JSON payload, a rough upper bound (the YAML dumper is pure Python and ~150x slower)
    pydantic dumps the JSON-mode dump, measured like JSON
    XML exact, measured with the C serializer
    HTML a tag walk, about 10 % above the real size (rendering the soup is ~10x slower)
    SQL a strided sample of statements, formatted and extrapolated
    pickle exact, measured with the C pickler
    pandas/polars parquet in-memory / estimated size
    pandas, polars CSV sampled every n-th row and extrapolated
    .npy, .npz array payload plus the npy header
    images uncompressed pixel payload

    estimated 39 written 39

    Writing a serialized dictionary as a directory tree¤

    write_structure lays a dictionary of primitives and files out on disk:

    • primitives are collected in __index__.yaml inside the directory,
    • files are written next to it, named after their key,
    • nested dictionaries and lists become sub-directories named after their key,
    • the __index__.yaml of a list directory holds a YAML list, with None at the positions taken by files and sub-directories, whose files are named after their position.

    ['index.yaml', 'image.png', 'meta', 'size'] name: thumbnail

    author: me

    thumbnail [2, 2] {'author': 'me', 'tags': ['a', 'b']} image.png

    Files read back as LocalFile handles, so they can be passed straight to deserialize. Rewriting a tree from its own structure (write_structure(read_structure(path), path)) is safe: each file's content is read before the entry it replaces is removed.

    A key must be one path component and must not be __index__: the key decides a file name, so a key such as ../outside or an absolute path would write outside the tree, and __index__ would take the name of the index. Both raise ValueError before anything is created. Replacing a key with a value of another shape (a file over a sub-directory, a primitive over a file) removes the old artifact instead of leaving it to shadow the new value; keys the new structure does not mention are left in place.

    Writing a serializer for your own type¤

    Subclass Serializer[YourType, TargetHint], implement serialize and deserialize, and register an instance. The class's type arguments are what selection reads, and each member of the target union becomes a declared format:

    1.5,2.5 1.5,2.5 Point(1.5, 2.5)

    CommonSerializer supplies the target handling: _resolve_target turns a target type or a file_factory into the file to write to, and returns None when the target is a plain value; __lossless_mimes__ declares which of the declared MIME types round-trip exactly, and __lossless_values__ whether the plain-value target does.

    The Serializable protocol¤

    When the object itself knows how to serialize, implement the protocol instead of a serializer: __serialization_targets__, __deserialize__, __serialize__ and __estimate_serialized_size__. serialize, deserialize and estimate_serialized_size then dispatch to the object:

    hello hello 5

    Traps worth knowing¤

    • A target names its format. A bare File hint matches nothing: ask for File[Literal["application/json"], TextIO], or pass a file_factory and let the serializer pick its default format. The factory decides where the bytes go, the target type decides what they are.
    • A failed encode does not truncate an existing file. Text payloads are built before the target is opened, so a value the serializer rejects leaves the previous content intact.
    • Object arrays are refused for .npy/.npz. Writing them would require pickle and loading them would require allow_pickle=True; convert the array to a concrete dtype first.
    • Losslessness is per format, not per serializer. Asking for lossless=True with a CSV target has no candidate even though the same serializer writes lossless parquet.
    • A plain-value target can be lossy too. SQL and HTML re-render the object, so serialize(soup, str) needs lossless=False exactly like the .html file does.
    • A missing pair raises ValueError. serialize and deserialize name the object type, the target and the active scope in the message.

    The public functions (serialize, deserialize, get_serializers, estimate_serialized_size, register_serializer, read_structure, write_structure), the Serializer and Serializable protocols, the scope classes and the shipped drivers are documented in the API reference and its submodules (base, common, local_fs).
